🚀从一个需求到可玩的海战游戏：Qoder跨设备开发完整实战！

一句话概括

一份需求文档喂给 Qoder，九分钟做出海战游戏，还让另一台 Mac mini 替你在后台跑测试。

blue

核心内容

一、起点：一份”小学生都能对着测”的规格文档 UP主没有一上来就让 AI 写代码，而是先写了一份需求与规格文档，把船的移动方式、开炮逻辑、操作后应出现的反馈都写清楚，并且明确划分版本边界——第一版做哪些功能、哪些暂时不做，”都在这里写得非常明确”。更关键的是一个容易被忽略的动作：文档里直接写上”具体的检查方式”，这样后面运行游戏时可以”对着这些需求一项一项来测试”。这是整条流程能闭环的前提——需求和验收标准是同一份文件。

二、第一轮：理解 > 写码 需求交给 Qoder 后，UP主第一步不是看代码，而是”先看一下他对当前项目的理解”，逐条检查有没有漏掉的需求、有没有自作主张增加不需要的功能。确认理解无误后，才进入执行环节。Qoder 的定位被概括为”以编程智能体为核心的工作台”，流程是”先理解项目规划任务，再通过编写代码和调用工具来执行”。每一项功能的验证方式是三件套对照：看这一项对应的需求 → 看它修改的代码 → 直接运行游戏看实际效果。UP主特别强调：”即使这里提示执行完成，我们也要实际操作一下”，确认画面和操作都没问题，再进入下一步。

三、迭代：用”改变说明书”代替”改代码指令” 第一版做出来后 UP主先亲自试玩，再把要调整的地方发回去，而反馈的写法有固定结构：说明刚才做了什么操作、希望实现什么效果、哪些功能不要改动。然后重复”修改—运行—试玩—再反馈”的循环。

四、转折：为什么要多设备——游戏测试会抢你的屏幕 这是视频里最有说服力的一个动机说明。UP主在自己电脑上办公时会”自动打开游戏窗口”，占用正在查看文档的窗口，”非常影响我的工作”。于是把开发和试玩留在手边的 MacBook（方便随时写需求、看进度、直接试玩），把游戏测试丢给远程 Mac mini，让测试时调出的窗口和产生的声音都留在远端，本地可以继续编辑文档。连接步骤很具体：两台机器都在设置里进入”设备连接”，远端 Mac mini 勾选”允许连接本机”并”生成配对码”，本地 MacBook 填入远端的 IP 地址、端口号和配对码，命名设备（如”Mac mini”）后添加即可。之后在本地选中远端工作区，确认项目版本与测试需求一致，项目文件和代码仓库通过 GitHub 同步。

五、测什么、怎么测：脚本与人工分开记账 发给远端的测试提示词里写明了：先检查环境和现有测试，再检查已实现的玩法，需要手动操作的单列出来，发现问题先保存记录、等确认后再修改。第一轮记录的结构被明确拆成两块：”脚本测试和人工试玩要分开”，脚本检查了哪些内容就对应哪些结果，画面和操作则需实际查看。之后还补充了一轮”重复执行同一个操作、对比前后状态有没有变化”的测试，结果”这一轮没有发现任何失败项，所以暂时不需要修改代码”。但 UP主保持了清醒：”这只能说明这些检查在当前条件下通过”，画面、操作手感和未覆盖的流程仍要继续检查——这也是他强调测试记录价值的原因：能看清哪些执行了、哪些通过了、哪些没覆盖，”不用只看一句任务完成的回复”。最后他同步 GitHub 代码、查看测试报告（分别看通过、失败、未覆盖三类），再亲自试玩确认操控、画面和反馈，才算收工。

记忆锚点

  • 【同一份文件既是考卷也是答案】 需求文档里预先写好检查方式，AI 交付时你才有尺子可量。
  • 【先看它懂没懂，再看它写没写】 交付前先审”对项目的理解”，防止漏需求、也防止加戏。
  • 【提示词三件套：我做了什么 / 我要什么 / 你别动什么】 迭代反馈的固定结构，把”别改坏”写进指令。
  • 【开发留手边，噪音扔隔壁】 游戏窗口和声音会抢屏幕，测试放远端设备，本地照常办公。
  • 【”任务完成”四个字不算验收】 报告要拆成通过 / 失败 / 未覆盖，最后还得人手玩一遍。
orange

关键要点

  • 要点一：验收标准要前置进需求文档
  • 原文引用：「然后再写上具体的检查方式……我们就可以对着这些需求一项一项来测试」
  • 案例还原：UP主在规格文档中写清船怎么移动、怎么开炮、操作后出现什么效果，并划定第一版做哪些、哪些暂时不做，同时附上检查方式。结果是后续每一轮测试都能直接对着文档逐项比对，而不是凭感觉判断”做好了没”。

  • 解读：把”怎么算完成”提前写死，是把 AI 产出变成可验收交付物的最低成本手段。

  • 要点二：第一道关卡是”理解审计”，不是代码审查

  • 原文引用：「这里我会检查有没有漏掉的需求，有没有增加我不需要的功能」
  • 案例还原：需求交给 Qoder 后，UP主先查看它对当前项目的理解，确认无遗漏、无自作主张的新增功能，才让它进入规划任务与写代码阶段；后续每项功能再走”需求—代码—实机效果”三重对照。

  • 解读：AI 的偏差往往在理解层就发生，越早拦截越省返工。

  • 要点三：完成的提示 ≠ 完成

  • 原文引用：「即使这里提示执行完成，我们也要实际操作一下，以便确认游戏画面还有操作都没有问题」
  • 案例还原：每次 Qoder 报告执行完成，UP主都实际运行游戏试玩，检查画面与操作是否符合要求，确认后才继续下一步；视频末尾也专门做了人工试玩（明确说明”并不是 coder 在执行测试”）后才判定通过。

  • 解读：自动化的自检覆盖不了手感与画面，人机双检是这条流水线的固定动作。

  • 要点四：多设备互联的真实价值是”隔离干扰”

  • 原文引用：「它会打开这个游戏画面，所以当我在使用这台 MACBOOK 进行工作的时候，非常影响我的正常工作」
  • 案例还原：UP主日常办公时游戏测试窗口会自动弹出、占用文档窗口并产生声音。他把测试任务派给远程 Mac mini（通过配对码 + IP 端口连接，GitHub 同步代码），测试的窗口和声音全留在远端，本地继续编辑文档，需要时再回到 Qoder 查看进度与结果。

  • 解读：多设备协作不是炫技，是把”会抢注意力”的任务物理外移。

  • 要点五：测试记录要分账，报告要看三类

  • 原文引用：「脚本测试和人工试玩要分开，脚本检查了哪些内容就对应哪些结果」「这里需要分别查看通过失败，还有没有覆盖的内容」
  • 案例还原：第一轮记录把脚本检查项与人工试玩项分开列出；补充测试时写入明确的检查条件，重复执行同一操作对比前后状态，该轮无失败项故不改代码；最终报告按通过、失败、未覆盖三类分别查看，再结合人工试玩判断整体效果。
  • 解读：只看”任务完成”的回复会漏掉未覆盖的盲区，分账记录才能指导下一轮测什么。

三大职业视角洞察

gold

① 市场调研 & 用户研究

  • 新洞察：视频里”需求文档 + 检查方式同写”的做法，本质是把研究结论转成可验证假设。UP主对 AI 的第一道检查是”有没有漏需求、有没有加不需要的功能”——这和审调研提纲是否跑题是同一套动作。
  • 可借鉴方法：① 验收标准前置：任何调研/可用性测试脚本，先写清”什么结果算通过”；② 双重记录法：脚本化检查项与人工观察项分表记录，避免用一句”整体感觉不错”下结论；③ 重复操作对比：同一操作执行两轮看状态是否变化，可迁移到可用性测试中的一致性问题排查。
  • 被揭示的坑：UP主明确提醒”这只能说明这些检查在当前条件下通过”，画面、手感、未覆盖流程仍需人工查看——自动化检查的覆盖率幻觉，是用户研究里最容易踩的坑。

② 品牌推广 & 营销

  • 新洞察：视频的传播钩子是”一个需求 → 一个可玩的游戏”，而非工具参数罗列；动机叙事（游戏窗口抢占办公屏幕）比功能列表更有代入感。
  • 可研究的手段：① 流程透明化——把”文档→理解审计→编码→实机验证→迭代”全链路摊开给人看，比成品展示更有信任感；② 用具体痛点开场（窗口被占用、声音干扰），让”多设备互联”这个抽象能力有了场景锚点；③ 结尾提供”验证信息见视频简介”，把好奇心导向可核验的细节。（本条为解读/推论）

③ 电商运营

  • 新洞察：这条流水线给”多环节协同交付”提供了一套可抄的作业结构：需求与验收同源、执行与验证分离、记录分账。
  • 可参考策略：① 把”检查条件”写进任务单，减少来回扯皮；② 把”会产生干扰/噪音”的动作外移到另一环境执行（类似客服、压测、批量任务放到独立通道）；③ 结果按”通过 / 失败 / 未覆盖”三类复盘，而不是只看完成率。
  • 用户旅程发现：UP主反复强调”提示完成 ≠ 完成”、”不用只看一句任务完成的回复”——对应到转化路径，就是别把系统回执当作用户满意，关键节点仍需人工复核体验。（本条为解读/推论，视频未涉及电商具体内容）

④ 智能硬件 PM（AI时代新定义）

  • AI 真正发挥作用的阶段：在本视频范围内，AI 承担的是”理解需求 → 规划任务 → 编写代码 → 调用工具执行 → 输出测试记录”这一软件闭环；对硬件 PM 的类比启示是：需求解析、任务拆解、脚本化自检、结果记录这几类”信息处理型”工作，已可交给智能体执行。
  • 边界在哪：视频给出了清晰的边界证据——UP主必须亲自做的三件事：① 写清需求与检查标准（文档是人写的）；② 审计 AI 对项目的理解是否正确（防漏防加戏）；③ 实机试玩确认画面与”操作手感”（原话强调人工试玩”并不是 coder 在执行测试”）。映射到硬件，手感、体验、实机表现这类需要人判断的部分，仍是 PM 不可外包的环节。
  • 流程与职责信号：本视频没有涉及 ID 设计、MD 堆叠、电子设计 demo 的任何内容，无法据此判断 AI 在这些硬件环节的能力边界（不做外推）。但可观察到两个可迁移的信号：一是”多设备分工”——把高干扰任务（如测试）放到远程设备执行，类似硬件团队把验证放到独立实验室/样机环境；二是”版本边界 + 验收清单 + 分账记录”三件套，可作为 AI 辅助硬件项目管理的流程模板。（本条为解读/推论）

  • 「这只能说明这些检查在当前条件下通过」（中段）——对测试结论边界的自觉，比任何”全部通过”的截图都可信。
