想让AI自己迭代先把验证做好

晓辉博士 · 2026-11-03
cyan

一句话概括

想让AI自我迭代？先把“验收标准”焊死，否则迭代越多垃圾越多。

blue

核心内容

背景：AI自进化热潮下的冷思考。 UP主（晓辉博士）开头提到，最近大家都在讨论AI agent的“自进化”“自己迭代”“自己净化”，包括Anthropic内部传出“26%的工作已可以交给AI自动化研发”（UP主明确说这是L4级别而非L5）。很多博主也在分享自己的自进化体系，比如loop、recursive等循环迭代机制。UP主自己也非常好奇这些agent到底怎么循环起来，很想让自己的agent也实现。但研究几天后发现一个关键前提：一定要可验证。

核心观点：不可验证，就别谈迭代。 UP主的判断非常直接：如果你的skill不能100%达到交付要求和标准，你不能充分信任agent能实现目标，那么让它迭代起来“只会产生更多的垃圾、更多的AI slop”，你会花更多时间去验证它的产出，“没有解放任何的自己的注意力”。这里他引出一个关键词——verification tax（验证税）：现在很多工作确实可以交给AI做，但验收要花额外时间，“甚至三四十%的时间都是花在验收上”。所以把验证体系写清楚、写好，是让AI自己循环、自己迭代的关键。

案例一：Groq Bot团队的verification skill（分两部分）。 UP主认真研究了Groq Bot团队potato分享的验证技能，这个团队做软件开发，希望agent能自己做验收、自己识别问题——比如用户反馈后改进，软件是不是真的跑通了，不用人再重复验证。他们的verification skill分两块： - feature map（功能地图）：agent来了之后知道这个软件是干嘛的、上下文是什么样、任何功能去哪里找。UP主的解读是：很多软件开发经验留在工程师脑海中，feature map就是把这个上下文告诉agent，“这样你就不用一遍一遍地教他了”，相当于agent了解软件地图的入口。 - CLI（command line interface，命令行界面）：把很多能力封装起来，比如agent操作电脑要用哪些工具、有哪些常用脚本可直接调用，把可复用的能力模块（日志、回滚、审查、交付等）全都封装好告诉agent，成为它可用工具的集合。UP主说自己作为外行是这么理解的。

案例二：UP主改造自己的录音转写工作流（前因后果完整）。 他反思自己原来的录音转写工作流：本质上skill就是一条条原则，大部分以文字形式存储，告诉agent要做哪些事。这导致交付时“验证全都是不可控的”，没办法根据强规则的校验去看它到底有没有完成要求和执行，属于“非常不成熟的一个skill”。改造后实现两个效果：一是把确定性要验证的环节交给脚本验证；二是把确定性、agent可重复使用的工具模块封装成CLI，这样agent不需要每次都重新写代码——UP主说这“也是非常被偷懒的一件事”（口播原意：省事），这次改进对他“非常的大”。

验证的五个层次（potato分享，UP主转述）。 前两层是“强验证”： 1. code base（代码仓库）：对应录音转写就是“好的样例非常重要”。如果agent能参考非常好的样例，就不会出那么多错，“照葫芦画瓢”。potato的观点是：如果代码本身一团乱，AI agent只会显得更乱。UP主延伸解读为“熵减的过程”——不能把非常乱的东西交给agent；对应知识工作者，就是你想清楚哪些东西放心让agent参考，“就像你交给一个实习生一样：好的，这个东西你参考这个标准去做吧”，这个金色标准（golden）要给它参考。 2. 形式化的检查：必须跑一遍脚本才能验收的硬性审查。对应知识工作就是脚本，比如完整性、字数到底有多少、是不是把所有上下文都核对清楚了，这些都可以写脚本验证。

后三层是“弱验证”：一些规则、一些skill、一些格式化偏好（比如字幕多大、录音转写的节奏口吻、不同人是第一人称还是第三人称），这些只能给agent提供参考，“但他是不是执行，我没有办法去验证”。所以UP主的结论是：尽可能让前两项变得更强，这是验证最必要的基础。

skill改造该做什么 + 自我进化的记录需求。 改造方向：先把标准写清楚——你的录音转写/视频剪辑什么样算满意、什么不能忍、什么一定要agent审查做到、格式标准大概什么样，尽可能告诉agent；这些信息“重复一次，然后能够把它沉淀下来，就能够持续去复用”。另外，skill做成之后能不能自己进化？比如下次用录音转写又发现问题，能不能让agent迭代这个skill——所以还需要一个地方记录每一次的变化。

最终结论（信任类比）。 UP主总结：所有信息都是希望用一套非常严格的标准，让AI agent能放心接过手里的活，本质上就是“信任”——“什么情况下你会相信他能够帮你完成你的工作”，就像跟同事合作、带一个实习生，“什么样的情况下你就可以真的，我百分之百放心交给他了”。前期肯定要付出大量心血和时间打磨。他说：程序员已经非常了解要写测试，知识工作者这一步也非常必要——“你到底怎么算通过了你的验收，如果没有的话，那么你将来自迭代全都是白搭，你没办法去保证交付的质量”。UP主自谦是小白、刚起步，还在持续改造自己的录音转写和视频剪辑工作流，并把提升skill的工作流要求贴在评论区供大家拿去用，也欢迎大家在评论区分享自己平常怎么做验证，并称“验证是摆在全世界使用AI的人面前的一个难题，也没有人现在彻底解决了，大家都是探索阶段”。

记忆锚点

【验证税】交活容易验收贵，三四十%时间在“查作业”——不可验证的自动化=给自己加税。 【垃圾进垃圾出·熵减版】代码一团乱，agent只会更乱——乱的东西别交给AI，它会帮你放大混乱。 【两张地图一发子弹】feature map告诉agent“去哪找”，CLI告诉它“用啥工具”，脚本是那颗必须打中的子弹。 【实习生法则】你敢100%放心交给实习生，才敢交给迭代中的agent——信任是按标准攒出来的。 【测试驱动知识工作】程序员先写测试再写代码，知识工作者先写验收再谈自迭代——没验收，自迭代全是白搭。

orange

关键要点

  • 要点一：AI自迭代的前提是可验证
  • 原文引用：「你让agent自己迭代起来，有一个前提就是一定要可验证」「如果没有的话，那么你将来自迭代全都是白搭」
  • 案例还原：UP主原本想让自己的agent实现loop、recursive等自迭代，研究几天后发现：如果skill不能100%达到交付标准、不能充分信任agent，迭代只会产生更多垃圾和AI slop，人还要花更多时间验收，注意力一点没解放。他由此转向先研究验证体系。

  • 解读：给所有想“上自迭代”的人泼冷水——先建验收，再谈自动化。

  • 要点二：验证税是普遍难题

  • 原文引用：「很多工作确实可以交给AI做了，但是我们的验收要花额外的时间，甚至是三四十%的时间都是花在验收上」
  • 案例还原：UP主引verification tax一词说明当前现实：交付可以外包给AI，验收却回到人身上，且占比高达三四成；他最后强调“验证是摆在全世界使用AI的人面前的一个难题，也没有人现在彻底解决了”。

  • 解读：省下的执行时间会被验收吃掉——设计工作流时必须把验收成本算进去。

  • 要点三：强验证两层——好样例 + 形式化脚本

  • 原文引用：「如果你的代码本身就是一团乱，那么AI agent只会显得更乱」「把一些确定性的要验证的环节，我交给脚本去验证」
  • 案例还原：potato的验证五层次中，前两层是code base和形式化检查。UP主对应到自己的录音转写：好样例就是“金色标准”，像给实习生参考的范本；形式化检查就是写脚本查完整性、字数、上下文是否核对清楚。他改造后把确定性验证环节交给脚本，效果“非常的大”。

  • 解读：能写成脚本的绝不靠嘴说——强验证越多，信任越牢。

  • 要点四：把可复用能力封装成CLI，别让agent每次重写代码

  • 原文引用：「把一些确定性的AI agent可以重复去用的一些工具模块，我全给它封装成CLI，那这个时候他就不需要再去每一次都重新写代码」
  • 案例还原：Groq Bot团队的verification skill包含CLI部分，把操作电脑的工具、常用脚本、日志、回滚、审查、交付等能力模块封装好告诉agent。UP主借鉴到自己录音转写工作流，把重复工具模块封装，省去每次重写代码的麻烦。

  • 解读：工具化封装是agent稳定性的地基——能力模块化，输出才可控。

  • 要点五：弱验证只能参考，所以要尽量做强前两层

  • 原文引用：「那这个只能说我给到agent，让他提供参考，但他是不是执行，我没有办法去验证，所以尽可能的让你的前两项变得更强」
  • 案例还原：验证五层次的后三层——规则、skill、格式化偏好（字幕多大、转写节奏口吻、第一/第三人称）——UP主坦言无法强验证，只能作为参考给到agent。因此他的策略是集中力量强化code base和形式化检查这两层。

  • 解读：承认验证有边界，把资源压在能硬校验的地方。

  • 要点六：skill要能自我进化，必须记录每次变化

  • 原文引用：「下次我再去用录音转写的时候，我又发现了一些问题，然后我能不能让这个agent……这个skill能够迭代，所以他还是需要有一个地方能够记录这每一次的这些变化」
  • 案例还原：UP主把标准写清、沉淀复用之后，进一步提出skill的自进化需求：每次使用中发现新问题，要能让agent迭代skill本身，而这依赖一个持续记录变化的机制。
  • 解读：没有变更记录的迭代是失忆的迭代——进化需要“记忆”。

三大职业视角洞察

gold

① 市场调研 & 用户研究

  • 新洞察：UP主把“验证”类比为“带实习生”——你要先想清楚“什么样算满意、什么不能忍”，这本质上是需求标准的显性化。用户研究里最难传递的正是这类隐性标准，UP主的做法（把标准沉淀成可复用文档、用样例做金色标准）可以直接迁移到研究简报和洞察交付规范上。
  • 可借鉴方法：用“feature map”思路给agent/团队建“研究地图”（数据在哪、结论去哪找）；用“golden样例”作为分析报告的参考范本；用脚本做形式化检查（如字数、完整性、上下文是否核对），减少人工复核成本。
  • 被揭示的坑：UP主原话点明“很多经验是留在软件工程师的脑海中”——同理，研究者的判断标准常留在脑子里，不写下来，交给AI（或新人）就会走样；弱验证项（口吻、人称、格式偏好）无法强校验，别指望AI自动对齐。
red

② 品牌推广 & 营销

  • 新营销思路：UP主在视频末尾把“skill改进方案”贴在评论区供大家取用——这是典型的内容钩子+评论区沉淀的运营手法：用可复用的工具型内容换互动与讨论（他还主动征集“你们平常怎么做验证”），把评论区变成UGC方法论池。
  • 值得研究的传播路径：选题踩在“AI自进化”热点上，但给出反直觉结论（先别迭代，先做验证），用verification tax这类概念词制造记忆点；结尾自谦“我也是小白”降低距离感，鼓励评论区共创。
  • 可迁移点：品牌内容若涉及AI工作流，把“可下载/可复制的提示词或流程”作为转化钩子，比单纯讲观点更容易被收藏和二次传播。
cyan

③ 电商运营

  • 运营策略参考：UP主的核心逻辑是“确定性环节交给脚本，可复用工具封装成CLI”——对应电商运营，就是把可标准化的环节（如检查清单、合规校验、素材规格核对）做成脚本或模板，把不确定的（文案调性、视觉偏好）作为弱验证参考项，人来做最终把关。
  • 转化路径/用户旅程新发现：UP主揭示“验收占三四十%时间”的成本结构，提示运营自动化项目要先算验收账：自动化省下的执行时间如果被验收吃掉，净收益为零甚至为负。设计AI客服、AI上架、AI内容生产流程时，应优先把“验收标准”写进流程而非事后补查。
blue

④ 智能硬件 PM（AI时代新定义）

  • AI能真正发挥作用的阶段：按UP主的框架类推（解读/推论），AI在智能硬件PM流程中最适合先接管“可强验证”的环节——例如形式化检查类工作（规格表完整性核对、BOM/参数一致性校验、文档格式审查）；而ID图、MD堆叠、电子设计前期demo这类涉及大量隐性经验与审美/工程判断的环节，恰恰类似UP主说的“留在工程师脑海中”的上下文，需要先建feature map（把设计规范、参考机型、历史方案沉淀给AI）才谈得上让AI参与。
  • 边界在哪里：UP主明确“弱验证”项（偏好、风格、口吻）AI只能参考、无法保证执行——映射到硬件PM，审美取向、堆叠取舍、成本与体验的平衡属于弱验证区，PM必须亲自做最终裁决；他还强调“乱的东西交给agent只会更乱”，意味着流程和文档不规范时，AI介入只会放大混乱。
  • 流程/岗位演变信号：UP主说“程序员已经非常了解要写测试，知识工作者这一步也非常必要”——对硬件PM的信号是：未来PM的核心竞争力之一是把验收标准工程化（写检查脚本、建golden样例库、记录每次变更），PM角色从“传话协调”向“定义标准与验证体系”迁移。

精彩原句摘录

  1. 「你让它迭代起来，它只会产生更多的垃圾，更多的AI slop」（中段）——一句话点破盲目自迭代的代价，是整期视频的论点支点。
  2. 「如果你的代码本身就是一团乱，那么AI agent只会显得更乱」（中段，转述potato观点）——把“输入质量决定AI输出”讲得最形象的比喻，适用于一切AI协作场景。
  3. 「你到底怎么算通过了你的验收，如果没有的话，那么你将来自迭代全都是白搭」（结尾）——把“验证先于迭代”的行动指令钉死，值得作为工作流设计的第一原则。
  4. 「本质上就是信任……什么样的情况下你就可以真的，我百分之百放心交给他了」（结尾）——用“带实习生”的信任类比收束全片，是理解人机协作尺度的钥匙。
