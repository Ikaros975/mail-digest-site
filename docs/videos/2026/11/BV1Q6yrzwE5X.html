Agent没那么神秘，核心就是一个循环

清华姜学长 · 2026-11-25
cyan

一句话概括

Agent不神秘：问模型→执行工具→带回结果→再问，一个循环跑到底。

blue

核心内容（3分钟视频，信息量有限，按原片结构如实展开）

背景痛点（开头）：UP主以 Claude Code、Codex 这类编程 Agent 的实际使用场景切入，指出两个典型故障：一是“刚交代过的要求，它过一会就漏了”；二是“对同一个报错试了好几遍，最后卡在那”，而且用户“想帮它往下走，都不知道从哪一步开始看起”。这两个痛点构成了整个视频要解决的问题——Agent 的不透明性。

核心观点：Agent 的本质就是一个循环。视频用一个叫“NAGENT”（字幕原文如此）的中文开源教程所带的本地网页演示来说明。演示任务是“写个 hello 点 Python 并且运行”，全过程被拆成三步：

  • 第一步·写文件：模型先“看一眼工作区的目录”，然后左边显示一段演示用的思考文字，接着弹出工具请求页面，“问你允不允许写入”；用户点了允许，程序才真正写文件；写完左边多出一条工具结果，“告诉模型文件已经写好了”。
  • 第二步·运行文件：模型收到刚才那条结果后，请求运行命令；用户再点一次允许；命令跑完，脚本打印什么，左边就显示什么。
  • 第三步·汇报结果：模型看到脚本跑完，直接告诉用户“文件写好了，输出是什么”，这一次没有再请求工具，循环就停掉了。

UP主由此归纳出循环本身：“问模型下一步怎么去做，程序执行他请求的工具，把结果带过来，再问一次模型。”他强调：你“在输入框里只说了一句话，后台已经来回跑了好几轮”。

网页设计的巧思（记忆抓手所在）：页面左边是 Agent 的动作流水，右边是“每次调用模型的时候发过去的消息”——哪部分是系统提示、哪部分是你说的的话、哪部分是工具返回的结果，“都有标记”，旁边还估算各自占用的 token。UP主认为这个页面“最好懂的地方是，左右两边能对得上”：左边刚显示文件已写入，下一次调用模型时就能在右边找到这条消息，“模型知道文件已经写好了，靠的就是它”。

Token 与“遗忘”的因果链（关键结论）：这解释了为什么一句很短的需求可能用掉不少 token——每次调用都会带上当时保留的全部消息、读进来的文件、命令打出来的日志，“可能比你那句话要长得多”。而任务跑久后，有些 Agent 会“清理旧输出，或者把前面的对话压成摘要”，于是“之前交代过的细节，就有可能在这一步给他漏掉了”。这正是开头“要求过一会就漏了”的机理。

三种上手方式：①跑仓库自带的本地演示，用预写脚本模拟模型回复，API key 可留空，Mac 装 Python 3.10+，双击 web 下的 start.command，提示输入 API key 时直接回车进入演示模式；②看作者做的在线图解，浏览器打开即可，可点播放或一格一格翻，观察每次调用后上下文多了什么；③自己写，从第一课开始，“先用大约 100 行的 Python 写出最小循环”，之后再加工具、加权限，接着看 skills、MCP、子 agent、计划和记忆，前 11 课有可运行代码和图文版。UP主建议先跑演示，重点看一个地方：左边的工具结果怎么出现在右边下一次发给模型的消息里，“看懂这一步再决定要不要跟着写”。

实用建议（结尾）：项目是拿去学原理的，跟着写需要一点 Python 基础，接真实模型要准备 API key，项目默认可用 DeepSeek。日常排障口诀：卡住时“先看最后一步——他在等你确认，还是已经拿到了一个报错，又在重复同样的操作”；聊久了漏要求时，“先把关键限制和当前进度重新交代一遍”。

记忆锚点（4条）

【三拍循环】问—做—回：问模型、跑工具、带结果回来，再问一次 —— 对应“Agent 本质是循环”这一核心定义。 【左右对账】左边是动作流水，右边是消息账本，两边对得上，模型才“知道” —— 对应网页演示中最关键的可视化设计。 【上下文雪球】你一句话，它背一包：文件、日志全塞进每次调用，token 就是这么烧的 —— 对应“短需求耗不少 token”的解释。 【压缩即遗忘】摘要一压，细节就漏 —— 对应开头“刚交代的要求过会就漏”的根因。

关键要点（4条）

  • 要点标题：Agent = 循环，不是魔法
  • 原文引用：「这就是agent最基本的循环问模型，下一步怎么去做程序，执行他请求的工具，把结果带过来，再问一次模型」
  • 案例还原：演示任务“写 hello.py 并运行”——模型先看工作区目录、输出思考文字、请求写文件；用户点允许后文件写入，工具结果回传模型；模型据此请求运行命令，用户再允许，脚本输出回显；模型看到跑完，直接汇报，不再请求工具，循环终止。

  • 解读：把 Agent 祛魅成四步流程，任何卡顿都能定位到循环的某一拍（30字内适用对象：所有 Agent 使用者）。

  • 要点标题：每次调用都背着全部历史，token 花在你看不见的地方

  • 原文引用：「每次调用AH的都会带上当时保留的消息，读进来的文件，命令打出来的日志可能比你那句话要长得」
  • 案例还原：UP主用演示页右侧的 token 估算标记说明：你只说了一句“写 hello 并运行”，但每次发给模型的消息里包含系统提示、你的话、工具返回结果三块内容，各占 token；多轮之后总量远超用户原话。

  • 解读：想省成本、控延迟，必须理解上下文是被“背着走”的（适用对象：成本敏感的开发者与团队）。

  • 要点标题：上下文压缩是“漏要求”的头号嫌疑

  • 原文引用：「有些AG卷的会清理旧输出，或者把前面的对话压成摘要，之前交代过的细节，就有可能在这一步给他漏掉了」
  • 案例还原：对应开头现象——用户刚交代的要求过一会就漏。UP主的解释链条是：任务跑久→Agent 清理旧输出/把前面对话压成摘要→细节在这一步丢失→表现为“漏要求”。他给出的对策是“把关键限制和当前进度重新交代一遍”。

  • 解读：长任务中要主动“重述约束”，而不是指望 Agent 记住（适用对象：长时间跑 Agent 任务的人）。

  • 要点标题：卡住时先看“最后一步”

  • 原文引用：「你可以先看最后一步，他在等你确认还是已经拿到了一个报错，又在重复同样的操作」
  • 案例还原：开头提到的“对同一个报错试了好几遍，最后卡在那”，UP主没有给复杂调试法，而是给了一个分诊动作：检查最后一步处于“等用户确认权限”还是“拿到报错并在重复操作”——前者点允许，后者需介入。演示中每次写文件、运行命令都需用户点“允许”，说明权限确认本身就是常见的“假卡住”。
  • 解读：排障先分诊再深挖，避免盲目翻全流程（适用对象：所有被 Agent 卡住的用户）。

三大职业视角洞察

gold

① 市场调研 & 用户研究

  • 新洞察：视频开头的两个痛点（要求被遗漏、同一报错反复试、不知从哪看起）本质是用户对 AI 产品“过程不可见”的抱怨——这是 AI 工具类产品用户研究中可直接复用的访谈切口。
  • 可借鉴方法：NAGENT 的“左右对账”页面是一种把内部状态外化为用户可读界面的范例，做可用性测试时可观察用户是否第一眼能看懂“左边动作↔右边消息”的对应关系；UP主自己就把“重点看一个地方”作为引导，这提示研究脚本应聚焦单点而非全流程。
  • 被揭示的坑：token 估算、系统提示/用户话/工具结果的标记，是用户理解成本的关键；研究中若不区分这三类消息，就容易误判用户“不懂 Agent”的真实原因。

② 品牌推广 & 营销

  • 新营销思路：这是一个典型的开源教程型内容营销样本——用本地可跑的演示（API key 可留空）降低体验门槛，用在线图解降低理解门槛，用 11 课体系课程做留存，形成“演示→图解→跟写”的漏斗。
  • 传播路径：UP主把抽象概念（Agent 循环）转化为一个可点击的三步演示和一个“左右对账”的视觉记忆点，这种单点可视化天然适合截图传播与口口相传；结尾的排障口诀（看最后一步、重述约束）是可被转述的“金句资产”。
  • 解读：推广 AI 工具时，“让用户先看懂一步”比讲全貌更有效（推论）。
cyan

③ 电商运营

  • 可参考策略：演示中的权限确认弹窗（“你点了允许程序才会去写文件”）是转化路径上的关键节点——每一次工具请求都是一次“用户确认”机会，类似下单前的二次确认；若确认过多会造成流失（视频中写文件、运行命令各需一次允许）。
  • 用户旅程新发现：UP主把“卡住”分为“等你确认”和“重复报错”两类，这正是用户旅程中的两类流失点——前者是流程摩擦，后者是价值未兑现。运营侧可借鉴：先判断用户停在哪一类节点，再决定是简化确认还是提供帮助。
  • 解读：把 Agent 循环映射为“请求—确认—反馈”的旅程模型，对设计引导式转化有启发（推论）。

④ 智能硬件 PM（AI时代新定义）

  • 逐字稿只涉及软件编程 Agent（Claude Code、Codex、DeepSeek API），未涉及 ID 设计、MD 堆叠、电子设计 demo 等硬件环节，故不对硬件 PM 流程作任何延伸推断。
  • 可迁移的一条原则（明确为推论）：视频揭示的“循环四拍 + 工具结果回传”说明 AI 的能力边界在于每次动作都需工具执行与结果验证；对应到任何 PM 工作，AI 能加速的是“问—试—看结果”的迭代节奏，而“确认是否允许执行”的判断权仍在人手里——视频中每个写文件、运行命令的动作都必须由用户点“允许”，这就是边界的具象化。
