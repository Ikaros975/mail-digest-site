一分半钟，把 AI 写的项目画成一张地图

清华姜学长 · 2026-11-19
cyan

一句话概括

让 AI 把 AI 写的代码画成一张“能点开、能问话”的项目地图。

blue

核心内容

视频只有两分多钟，信息密度却不低，核心是一条“工具分工”的判断逻辑，外加一个完整的上手实录。

背景与问题分层。 UP主此前推荐过一个叫“read drive”的 skill（注：字幕音译，原文应为同类“读代码/追问式”工具），它的特点是不帮写代码，反过来向人提问，逼使用者把 AI 写的代码自己想明白。但评论区有同学反馈“方法挺好，但需要一题一题答下来，还是有点复杂”。UP主由此做了一个关键的需求拆分：这是两种不同的需求——第一种人想弄明白“这个项目为什么要这样设计”，那 read drive 这类追问工具适合他；第二种人卡在更前面一步，“AI替我写了一大堆东西，我连他到底做了什么都不清楚，更不知道里面有什么坑”。针对第二种需求，UP主推荐了一个叫 flow plan 的插件。

flow plan 做什么。 它会把项目读一遍，画成一张能点开的地图，每一块都用大白话写清楚是干什么的，块和块之间怎么连起来也都画出来。

完整实测案例（视频唯一的案例，必须讲全）。 UP主拿上次做过的项目“class 的 lm console”来试——这个项目干的活是：把同一个问题发给好几个模型，让它们互相去评 capacity（互相评判、打分），而且 UP主自己说“代码99%都是AI写的”。操作路径只有一句：在 cloud code 里说“帮我给这个app画一张地图”，等个一分半左右，地图就在浏览器里打开。打开后，整个项目被分成几块：用户看到的聊天网页、背后的主服务器、负责调用各家模型的中转服务、还有存放对话记录的文件夹；20几个单位文件，每一个都配了一条说明。此外地图打开时会带你走一遍导览，从“这个 app 是干什么的”开始。

更细的一层：可以直接向地图提问。UP主举例问“用户发出一个问题以后，背后都发生了什么”，地图分三个阶段讲清楚了——先让每个模型各自回答；再让它们匿名互相打分；最后由一个模型汇总出最终答案。每一步都能在地图上点到对应的那一块。

还有一道健康检查：顺手检查 AI 写的项目里常见的几个坑，比如密钥直接写进代码、接口不用登录就能调用等等，查到了还会给出修改建议。但作者自己声明（UP主转述）：健康检查只是一次快速检查，不是专业的安全审计，没查出问题也不代表就没问题。

边界与成本。 UP主明确提醒：本次只试了一个小项目，大项目会更加满（更庞大）、也更费额度；另外得用 cloud code 或 codex，界面是英文的。

关键结论： 手上有个 AI 帮你写的项目、但不太清楚它做了什么的时候，就用 flow plan 给它画一张地图。视频结尾 UP主顺带提了自己的“江学长 AI 学习圈”，现有 3000 多位同学每天更新精选 AI 资料与实战。

记忆锚点

  • 【两种卡点】 “想不通设计 vs 看不懂全貌”——read drive 治前者（追问式逼你思考），flow plan 治后者（画图让你看见），先分清自己卡在哪一步再选工具。
  • 【代码黑箱变图书目录】 20几个文件每个配一句大白话说明，如同给一柜子没标签的书贴上目录卡，点哪本开哪本。
  • 【一句话换一张地图】 就在 cloud code 里说一句“帮我给这个app画一张地图”，一分半钟浏览器里见——成本极低，所以值得先画再读。
  • 【地图能问话】 不只静态看，还能追问“用户提问后发生了什么”，答案能一步步点回对应模块——把抽象流程锚定在具体位置。
  • 【体检≠安全审计】 健康检查是“顺手量个血压”，查出问题给建议，没查出问题不等于没病。

关键要点

  • 要点一：先判断你卡在哪一步，再选工具
  • 原文引用：「有的人想去弄明白这个项目为什么要这样设计……但有些人卡在的是前面一步，就是AI替我写了一大堆东西，我连他到底做了什么都不清楚」
  • 案例还原：评论区同学反馈 read drive 好用但“一题一题答下来还是有点复杂”，UP主没有否定工具，而是把反馈拆成两类需求：偏“理解设计意图”的继续用追问式工具，偏“先看清全貌”的改用 flow plan 画地图。

  • 解读：选工具前先定位自己的卡点，否则工具再好也嫌重。

  • 要点二：把黑箱翻译成“大白话地图”是理解 AI 代码的最低门槛

  • 原文引用：「每一块都用大白话写清楚是干什么的，块和块之间怎么连起来也都画了出来」
  • 案例还原：class 的 lm console 项目被拆成聊天网页、主服务器、调用各家模型的中转服务、对话记录文件夹四类模块，20几个单位文件各配一条说明，打开还有导览，从“这个 app 是干什么的”讲起。

  • 解读：对“99%代码是AI写的”这类项目，先建结构认知比读代码更划算。

  • 要点三：能追问的地图，才真正把流程讲透

  • 原文引用：「你要是想知道用户发出一个问题以后背后都发生了什么，分三个阶段都讲清楚了」
  • 案例还原：阶段一各模型各自回答，阶段二匿名互相打分，阶段三由一个模型汇总最终答案；每一步都能在地图上点回对应模块。

  • 解读：做流程理解/交接评审时，把“口头流程”落成“可点位流程”效率最高。

  • 要点四：健康检查能兜住常见坑，但不能替代安全审计

  • 原文引用：「健康检查只是一次快速检查，不是专业的安全审计，所以他没查出问题也不代表就没问题」
  • 案例还原：健康检查针对 AI 写项目里的常见坑，例如密钥直接写进代码、接口不用登录就能调用，查到会给出修改建议；但作者明确声明其边界仅为快速检查。

  • 解读：把它当第一道筛子，别当合规背书；安全议题仍要另找专业手段。

  • 要点五：大项目更费额度，工具也有适用规模

  • 原文引用：「我们这次只试了一个小的项目，大项目呢会更加满，也更费额度」
  • 案例还原：本次实测的是小项目、耗时约一分半；UP主提示大项目地图会更庞大（“更满”）且消耗额度更多，另需 cloud code 或 codex、界面为英文。
  • 解读：先在小项目上验证价值，再决定是否对主干项目使用，控制成本。

三大职业视角洞察

gold

① 市场调研 & 用户研究

  • 最大启发是“从评论反馈拆需求”的方法论：UP主面对“方法挺好但有同学觉得复杂”的反馈，没有直接改工具，而是把反馈拆成两类需求（想懂设计意图 vs 想懂全貌），这正是一手反馈分析的标准动作——把“不好用”翻译成“他是卡在哪一步”。
  • 可借鉴的调研手段：用地图工具给调研/访谈做“结构导览”。视频中地图先讲“这个app是干什么的”，再给模块说明，最后支持追问流程（提问→各自回答→匿名互相打分→汇总），这套“总览—定位—追问”三层结构与用户旅程梳理是同构的。
  • 被揭示的坑：把“用户说复杂”当成工具缺陷会误判；实际是需求分层问题。另外，UP主对健康检查的边界声明（“不是专业的安全审计”）也是一种诚实的范围声明范本，提醒调研结论要标明适用范围。
red

② 品牌推广 & 营销

  • 一条清晰的内容承接路径：先推“追问式 skill”，评论区出现“复杂”反馈后，再出一条“针对另一种需求”的续集内容——用观众反馈反向选题，天然承接上一集流量。
  • 值得研究的传播点：“一分半钟”“说一句话就出图”“20几个文件每个都有说明”这些具体、可验证的低门槛承诺，比抽象讲原理更利于传播；结尾以“3000多位同学”的学习圈作为社群背书与转化钩子，是知识类 UP主常见的“内容—社群”闭环。
  • 启发：新品/新工具推广时，先讲清“你卡在哪一步、这个工具管哪一步”，比堆功能更能让人对号入座。

③ 电商运营 & 渠道管理

（说明：视频本身不涉及交易、转化、渠道等电商要素，以下为有限外推，明确标注为推论） - 可迁移的一点是“健康检查”式的前置风控清单：视频里健康检查会扫“密钥写进代码、接口免登录可调用”这类常见坑并给修改建议——推论：运营侧同样可建一份“常见坑快速检查表”（类比价格/库存/权限/活动配置的例行体检），但同样要声明“只是快检、不替代专业审计”。 - 转化路径上的新发现：视频没有电商案例，无法提供转化旅程证据；唯一可参考的路径是“内容（视频）→ 评论区 → 社群（学习圈）”，属于私域承接而非电商交易漏斗。

④ 智能硬件 PM（AI 时代新定义）

（说明：视频未涉及任何硬件、ID 图、MD 堆叠、电子设计 demo 的内容，因此不能给出该项的直接结论；以下仅就“AI 在软件项目上的作用边界”做类比解读，标注为推论） - AI 当前真正做成的阶段：视频证据显示，AI 能对“已有代码的项目”做理解层工作——读一遍、分模块、用大白话写说明、画出连接关系、支持按问题追问流程，一次约一分半，适合小项目。推论：这类“读+画+答”的能力，最接近硬件项目中“把散乱的方案、文档、模块关系整理成可视图”的需求，但视频没有硬件案例支撑。 - 边界在哪里：视频给出两条明确边界——一是健康检查“只是快速检查，不是专业的安全审计”，二是大项目“更满、更费额度”。推论到硬件：AI 可以产出结构化说明和初筛清单，但判断“能不能上线/是否安全/是否可量产”这类责任性结论，PM 仍须自己或专业角色拍板。 - 岗位职责演变的信号：视频里“代码99%都是AI写的，人连它做了什么都不清楚”这一现象，直接对应 PM 未来的一个新职责——先让团队看懂 AI 产出了什么，再谈设计意图；工具分工（追问式 vs 画图式）也提示 PM 要按“卡点层级”配置工具，而不是指望一个工具通吃。

适合人群

手上有一堆“AI 帮你写完、你却说不清它做了什么”的项目，想用最低成本先看清结构、顺便筛一遍常见坑的人。两分钟内看完就能上手试，尤其适合非重度开发、以项目理解与协作为主的人。
