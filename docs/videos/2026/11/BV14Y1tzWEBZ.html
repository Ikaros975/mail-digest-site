AI也开始“做梦”了？2026年最值得听懂的5个Agent新词

清华姜学长 · 2026-11-27
cyan

一句话概括

AI不再比分数，比的是谁把「工位、SOP、团队、记忆、权限」配齐了。

blue

核心内容

视频围绕 Anthropic 谈 agent memory 时使用的一个词——「dreaming（做梦/居民/积木，字幕音译不一）」——展开，UP主（清华姜学长）用自己的总结把当前 agent 领域最值得听懂的 5 个新词串成一套体系。全片用一个贯穿比喻：公司来了一位特别聪明的新同事，你让他每周做一份行业报告，然后看他要配齐哪些东西才能真的把活干成。

背景判断：UP主指出，「做梦」不是 AI 突然有意识，而是智能体完成很多任务后，会在空闲时回看自己的工作记录，把有用的经验整理成记忆，顺便纠正之前记错的东西。这个词之所以出现，是因为 AI 正在从「你问一句、他答一句」，变成一套能够连续做事的系统。

五个术语逐一拆解（以「新同事做周报」为线索）：

  1. harness（智能体运行框架）——光有一个聪明大脑不够，不能「直接靠大脑上班」。同事需要知道文件放哪、公司能用哪些工具、拥有哪些权限、失败后什么情况必须来问你。这套包在模型外面的运行系统就是 harness。UP主的定义是：模型像大脑，harness 是工位、电脑和公司规则。由此推出一个关键结论：同一个模型放进两个 AI 产品，干活效果可能完全不同，差距未必来自模型，而来自周围这套工作环境。

  2. agent skills（智能体技能）——新同事有了工位，还是不知道你们公司的简报怎么做：查哪些来源、怎么交叉核验、用什么模板、缺数据时怎么办。把这些保存成一套可反复使用的流程，就是 skills。UP主比喻为一份 AI 可以按需打开的 SOP，不用每次重新解释一遍，遇到对应任务自己就知道按什么流程做。

  3. multi agent（多智能体协作）——一份行业简报可能同时要查政策、看产品、分析数据，这时主 agent 会把三块工作分给三个 sub agent，每个子智能体有自己的任务和上下文，分头完成后由主 agent 汇总。UP主随即泼冷水：身体不是越多越好，只有能独立拆开的工作才适合并行；如果后一步必须等前一步完成，多叫几个 agent 反而增加沟通和核对成本。

  4. agent memory（智能体记忆）——工作时间一长，怎么把本周踩过的坑带到下一周？这就是 memory。呼应开头的「做梦」：agent 在空闲时回看日志、整理日记、修正错误，甚至给自己的记忆建立索引。UP主强调这本质上是一次离线复盘，不是人的做梦；而且 AI 写下来的记忆也可能出错，有记忆不代表可以跳过核验。

  5. persistent agent（持续型智能体）——普通 agent 领到任务、做完就停；持续型智能体可以长期在后台运行、监控变化，并在没有新指令时主动行动。UP主给的例子：持续收集用户反馈，发现同一类问题反复出现后，主动整理证据并创建工单。但他同时点出代价：越主动，权限边界越重要——什么时候可以看、什么时候可以改、每一步是否必须有人批准、出了问题能不能追溯，都要提前设计好。

收束：UP主把五个词串成一句话——harness 给工作环境，skills 给做事方法，sub agents 给一支团队，memory 和「做梦」让它积累经验，persistent agent 让它持续在线。结论是：下一阶段拉开 AI 工具差距的不再是模型分数，而是谁能把任务、工具、权限、记忆和人的审批，设计成一套完完整整的可靠工作系统。最后给了观众一个可操作的提问清单：看到产品说自己有 agent，别只问用了哪个强模型，要追问三句——他能碰到什么？他会记住什么？他做哪一步之前必须先问我？

记忆锚点

  • 【新同事上班】 聪明大脑≠能上班，还得有工位、电脑和公司规则——模型是大脑，harness 是工位。
  • 【按需打开的 SOP】 skills 就是把「我们公司简报怎么做」写成一张随时能翻的流程卡，不用每次重新教。
  • 【搬砖要能拆】 只有能独立拆开的活才配并行，串行任务多叫 agent 只是多开几场沟通会。
  • 【睡前写日记】 memory 是 agent 下班后翻日志、改错题、建索引，本质是离线复盘，不是意识觉醒。
  • 【越主动越要上锁】 persistent agent 能自己找活干，所以「哪一步必须先问我」要写死。

关键要点

  • 差距不在模型，在 harness
  • 原文引用：「同一个模型放进了两个AI产品里，干活的效果可能就完全不同了，差距未必来自于模型，而是来自于他周围的这套工作环境」
  • 案例还原：UP主用「新同事」设定说明——同一个聪明人，若不知道文件放哪、能用哪些工具、有哪些权限、失败后什么情况该来问你，就没法干活；这套包在模型外面的运行系统就是 harness。解读层面可推知：评估 AI 产品时，问「它能碰到什么」比问「它用哪个模型」更能区分实际效果（此为推论，原片未给具体产品对比案例）。

  • 解读：选工具先看环境配置，别只盯跑分。

  • 并行不是免费的

  • 原文引用：「只有能够去独立拆开的工作才适合并行，如果后一步必须要等前一步完成，那多叫几个agent反而会增加沟通，包括核对的成本」
  • 案例还原：UP主举的正面例子是一份行业简报同时要查政策、看产品、分析数据，主 agent 把三块分给三个 sub agent 分头做、主 agent 汇总；反面情形则是后一步依赖前一步的任务，此时加 agent 只增加沟通与核对成本。

  • 解读：拆任务前先画依赖图，能并行的才并行。

  • 有记忆≠可跳过核验

  • 原文引用：「AI写下来的记忆也可能出错，所以有记忆不代表可以去跳过核验」
  • 案例还原：UP主描述 agent 会在空闲时回看日志、整理日记、修正错误、给记忆建索引，称之为「离线复盘」；但紧接着提醒这套自写记忆本身可能出错，因此核验环节不能省。

  • 解读：把记忆当草稿，不当档案，关键结论仍要复核。

  • 主动性必须配权限设计

  • 原文引用：「他越主动，那权限边界就越重要，什么时候可以看，什么时候可以改，每一步必须有人批准，出了问题能不能追溯」
  • 案例还原：UP主举的持续型智能体场景是：长期在后台运行，持续收集用户反馈，发现同一类问题反复出现后主动整理证据并创建工单；由此引出对可看、可改、需审批、可追溯四个边界的前置设计要求。

  • 解读：给 agent 放权之前，先写好「刹车和行车记录仪」。

  • 三句话筛 agent 产品

  • 原文引用：「第一个他能碰到什么，第二个他会记住什么，第三个他做哪一步之前必须的要先问我」
  • 案例还原：UP主在结尾把整期内容压缩成这套追问法，对应 harness（碰到什么）、memory（记住什么）、权限与审批（哪一步先问人）三个维度。
  • 解读：现成的采购/选型 checklist，可直接拿去问供应商。

三大职业视角洞察

gold

① 市场调研 & 用户研究

  • 新洞察：UP主对 persistent agent 的描述本身就是一份用户研究的工作流蓝图——「持续的去收集用户反馈，发现同一类问题反复出现之后，主动整理证据，并且创建工单」。这提示调研角色的产出形态可能从「一次性报告」转向「常驻监控+证据归档+工单闭环」。
  • 可借鉴的方法：把调研流程 SOP 化（对应 skills）——查哪些来源、如何交叉核验、缺数据怎么办，写成可复用流程，既喂给 agent，也让人交接不失真。
  • 被揭示的坑：agent memory「也可能出错」，所以 AI 整理的反馈记忆不能当原始证据用，核验环节不可省。

② 品牌推广 & 营销

  • 新洞察：UP主的核心判断是「下一阶段真正拉开AI工具差距的，不再是模型分数」，而是完整工作系统的设计能力。对营销的启示是：对外讲 AI 能力时，卖点应从「用了多强的模型」转向「它能碰到什么、会记住什么、哪一步先问人」这类可信赖的系统叙述。
  • 可研究的传播路径：UP主示范了一种有效的科普结构——用「公司来了个聪明新同事」一个比喻贯穿五个术语，末尾给三句可复述的追问清单。这种「一个比喻+一句口诀」的内容设计，本身就是高记忆度的传播模板。
  • 注意：原片未涉及任何品牌投放或增长案例，以上为基于其论证结构的推论。
cyan

③ 电商运营

  • 新洞察：persistent agent 的「后台监控变化+无指令主动行动」模式，与电商运营中的持续巡检类工作（如反复出现的同类问题被自动归集为工单）在结构上同源。UP主举的例子正是「同一类问题反复出现→整理证据→创建工单」这一闭环。
  • 可参考的策略：多 agent 协作的适用边界同样适用于运营任务拆分——只有能独立拆开的环节（如政策核查、产品信息核对、数据分析三线并行）才适合并行，有前后依赖的链路（如下一步必须等上一步）加人反而增加核对成本。
  • 用户旅程的发现：UP主未直接讨论转化路径或用户旅程，此维度原片无直接素材，不做延伸。

④ 智能硬件 PM（AI时代新定义）

原片未涉及 ID 设计、MD 堆叠、电子设计 demo 等硬件开发环节，因此不对「AI 能否打通 ID→MD→电子 demo 全流程」作判断。但片中五个术语可作为硬件 PM 在 AI 时代职责演变的信号来读（以下为推论）： - harness 思维：同一个模型放进不同产品效果不同，差距来自「工位、电脑和公司规则」。映射到硬件团队，即 PM 要把工具链、权限、失败升级路径设计好，而不是只挑最强模型。 - skills 思维：把团队反复使用的流程（来源、核验、模板、缺数据预案）固化成可复用 SOP，这是 PM 可直接迁移的组织资产。 - multi agent 边界：只有可独立拆分的模块才适合并行，串行依赖处强行并行只会增加沟通与核对成本——这与硬件开发中强依赖环节的管理逻辑一致，但原片未举硬件案例。 - memory 与核验：AI 自写的记忆可能出错，「有记忆不代表可以跳过核验」——PM 对 AI 产出的任何中间结论仍须保留复核关卡。 - persistent agent 与审批：越主动的智能体越要提前定义「什么时候可以看、什么时候可以改、每一步必须有人批准、出了问题能不能追溯」，这正是 PM 在引入自动化时该写的边界文档。 - 必须亲自做的事：按片中的逻辑，PM 不可外包的是边界与审批的设计——即回答「他做哪一步之前必须先问我」。
