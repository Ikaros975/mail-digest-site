# 拆解5个经典Harness

## 一句话概括
五个 harness 拆开看，选自建框架先定五件事：内核、循环、上下文、工具、安全。

## 核心内容

UP主晓辉博士最近在“搓自己的 harness”，这期接着前一天的评测话题，横向拆解五个日常常见的 harness 产品，想回答一个问题：如果你想自建一个 harness，该参考什么、里面到底有哪些核心构成要素。

**五个样本，五种“内核”取向。** UP主点名的五个 harness 各有性格：①“派”（Paid/Pie，音译）走极简路线，用“最小必要原则”把大模型需要的工具、上下文、记忆界定清楚；②HERMES 对应的是“learning loop”方向——定期优化 skill、迭代、清理上下文和记忆，UP主认为这跟他自己想做的方向比较一致；③open cloud 非常火热，但问题是工具非常多，记忆和上下文冗余冗杂，所以大家用起来都觉得“比较消耗”；④deepseek harness 是插件体系，基于 CORDIS 内核的插件框架，常用功能能力都做成插件，“即插即拔”；⑤LMA（音译，UP主称“昨天也说过”），是个人开发者 yet one 做的产品，UP主最近在用，觉得“非常顺手”，特点是靠用户一点点提反馈迭代出来，一开始面向 coding agent 和程序员群体。

**第一个构成要素：内核/基本理念。** UP主强调这五个产品各不相同——有极简理念的、有做 learning loop 迭代循环的、有把记忆角色上下文定义得非常清楚的（如 open cloud）、有插件式的（deepseek、LMA）。所以你自建时第一件事不是写代码，而是先定“你的基本理念是什么”。

**第二个要素：loop，即任务何时算结束。** 这里要提前跟模型约束好、规划好一连串问题：结束由模型定义还是用户定义？用户定义的话怎么算完成？如果是迭代，迭代多少次、尝试多少次？不成功是否就停止？UP主把这归为“循环”与“停止/截止”的设计。

**第三个要素：上下文与记忆。** 要不要有记忆？要不要能形成对用户长期需求的理解？这是壳层面必须回答的问题。

**第四个要素：工具（给模型配“手和脚”）。** 这里有一个非常好的对照案例：派这个最精简的 harness 只有四个工具——read、write、edit，再加一个 bash（读写改 + 调用命令行），而有了 bash 其实其他工具也能调用了。反过来，open cloud 一开始默认安装的工具就非常多，方便大家直接调用、通用性更强；但代价是——**做一个不相关任务时，它也要加载这些工具的上下文信息，对 token 就是冗余消耗**。UP主认为目前“还可以”的是 HERMES：调用工具相对少，而且不是一次性全部披露给模型使用。这就是“工具多=通用性强但费 token”的权衡案例，前因后果讲得很清楚。

**第五、第六个要素：multi-agent 与安全，外加扩展。** 要不要有子 agent 与主 agent 的交互？子 agent 之间要不要通信？子 agent 还能不能再派生子 agent？派这种肯定没有，HERMES 等则有更多拓展。安全上要决定：模型跑在沙箱里怎么给权限，是隔离在沙箱，还是一开始就给无限权限。扩展上，比如现在大家会写 MCP 去调用别人提供的服务——**派最早的极简理念是不支持 MCP 的，但后来经过一段时间用户反馈和权衡，现在也开始支持 MCP 了**，UP主把这个作为“扩展是要考虑的节点”的实例。

**收尾的观点。** harness 的核心作用是帮大模型管理“该怎样响应用户需求”：单个模型很多任务难以迭代起来——验收、循环设计、停止截止、记忆沉淀、上下文有限，都是问题；壳就是让模型跑得更稳、更持久、更有效响应需求。而像 WalkerBarry（音译）等国内 agent 框架，还会解决长尾问题，比如报错怎么处理、权限或安全问题时怎么处理。对“非开发者别折腾 harness、把专业的事留给专业的人”的说法，UP主的回应是：他折腾的初衷是了解大模型到底该怎么驾驭、普通人有没有机会学习和理解；从零手搓（而非借鉴别人）有助于理解开发者每天投入的方向到底是什么。但他也明确区分：自己用和做成产品给别人用差别很大，bad case、边缘 case 是否充分考虑影响很大；门槛非常低，关键是能不能让其他人更好用起来、拿到用户反馈和数据。他还提到前两天 T3 被讨论较多的“偷用户数据”问题——大家贡献的数据会被拿去做统计、分析，存在较大安全隐患，“就看你自己的选择了”：自己手搓个个放心，还是用别人的、相信对方能给你足够支持，是完全不同的两件事。

## 记忆锚点
- 【四把工具走天下】派只有读、写、改、bash 四件套，一把 bash 通吃其余——工具越少，token 越省，模型越不晕。
- 【工具多=背包重】open cloud 工具全但样样加载，等于出门背整个工具箱，干不干活都先付行李费。
- 【先定魂，再定壳】五个 harness 差在“理念”这一层，自建第一步不是写代码，是回答“我要极简还是要 learning loop”。
- 【结束权归谁】loop 设计的灵魂一问：任务算完成，是模型说了算还是你说了算，试几次不行就喊停。
- 【派也会低头】极简派最初拒绝 MCP，被用户反馈磨到支持——理念是起点，用户反馈是方向盘。

## 关键要点
- **五样本五种内核**
- **原文引用**：「它的一个内核，或者说你的一个基本的理念到底是什么……这五个其实各不相同」
- **案例还原**：UP主列举派（极简、最小必要原则）、HERMES（learning loop、定期优化 skill 与清理上下文记忆）、open cloud（工具多、记忆上下文冗余）、deepseek harness（CORDIS 插件体系、即插即拔）、LMA（个人开发者 yet one 做、靠用户反馈迭代、起于 coding agent）。背景是 UP主自建 harness 需要参考对象，过程是横向拆解，结论是“理念层决定产品形态”。
- **解读**：给准备自建 agent 框架的人一个选型坐标系。

- **loop 的完成与停止必须提前约束**
- **原文引用**：「到底大模型什么时候算结束了，一个任务怎么定义完成……迭代多少次，尝试多少次，如果不成功就算停止了」
- **案例还原**：UP主没有给具体产品案例，而是把 loop 拆成一组必须预先与模型约定好的问题：结束由模型还是用户定义、用户定义时完成的判定标准、迭代/尝试次数上限、失败后的停止条件。这些都属于“提前跟模型约束好、规划好”的设计项。
- **解读**：不做停止条件设计，agent 就会陷入无限循环或半途而废。

- **工具数量是通用性与 token 成本的权衡**
- **原文引用**：「带工具多的一个问题，就是它的通用性会更强，但是……他也要加载这样的一些上下文的信息，所以对 token 来说就是一个冗余的消耗」
- **案例还原**：对照案例很完整——派只有 read/write/edit/bash 四个工具，靠 bash 兜底调用命令行；open cloud 默认安装工具极多，为的是方便直接调用、通用性强，代价是不相关任务也要加载这些工具的上下文，白烧 token；HERMES 工具较少且不一次性全披露给模型。UP主据此判断 HERMES 目前“还可以”。
- **解读**：给模型配工具不是越多越好，按需披露才是省钱又省心的做法。

- **极简理念也会被用户反馈修正**
- **原文引用**：「派最早他的极简理念中，它是不支持这个MCP的，但是后来经过一段时间用户的反馈和权衡，他现在也开始支持这个MCP了」
- **案例还原**：背景是派以极简为内核；起因是用户反馈与权衡；过程是经过一段时间后立场松动；结果是这个最初拒 MCP 的极简 harness 现在支持 MCP。UP主把它作为“扩展”这一构成要素需要持续考虑的节点。
- **解读**：理念是起点不是教条，用户的真实需求会推着产品改。

- **自己用≠做成产品**
- **原文引用**：「你要开发成一个产品，和自己用还是差别挺大的，包括这里面的 bad case，包括边缘的一些 case 有没有充分考虑」
- **案例还原**：UP主自述手搓的初衷是理解大模型该怎么驾驭、普通人有没有机会学习理解，并认为从零手搓有助于理解开发者每天投入的方向。但他明确划线：做成产品给别人用，关键在于 bad case 和边缘 case 是否被充分考虑、能不能让别人更好用起来、能不能拿到用户反馈和数据。他还提到 T3 被讨论的“偷用户数据”问题——贡献的数据被拿去做统计、分析，存在较大安全隐患，选择自搓还是用别人的，是“完全不同的两件事”。
- **解读**：想从玩具走向产品的人，先想清楚反馈闭环和数据信任。

## 三大职业视角洞察

### ① 市场调研 & 用户研究
- 新洞察：视频本身就是一份“竞品拆解”模板——按内核理念、loop、上下文记忆、工具、multi-agent、安全、扩展七个维度横向对比五个产品，而不是罗列功能。做竞品分析时可借用这套维度表。
- 可借鉴方法：UP主反复强调“用户反馈驱动迭代”——LMA 是靠用户一点点提需求磨出来的，派因用户反馈从拒 MCP 转向支持 MCP。这提示研究角色要盯“产品理念与用户诉求的摩擦点”，那里往往是需求洞察的富矿。
- 被揭示的坑：工具多被当成卖点（open cloud），但真实使用中是 token 冗余消耗，用户感受是“比较消耗”——功能清单式的调研会误判用户真实体验。

### ② 品牌推广 & 营销
- 新思路：五个 harness 的定位差异其实是五种“品牌人设”——极简派、学习循环派、全能派、插件派、社区共创派。做传播时可把“理念”作为差异化叙事的核心，而不是拼功能数量。
- 值得研究的路径：LMA 的成长路径是个人开发者 + 用户反馈共创，这类“社区共建”叙事在开发者群体中自带传播力；HERMES 的“少而精、不一次性全给”也可包装成克制、专业的品牌调性。

### ③ 电商运营
- 可参考策略：open cloud 的“默认装满工具”类似电商的“满配 SKU”，上手方便但成本转嫁给用户（token）；派的“四件套 + bash 兜底”更像精简 SKU + 万能入口，降低选择成本。SKU 设计与 agent 工具设计同理：多不等于好。
- 转化路径发现：视频提到关键不是门槛低，而是“能不能让其他人更好的用起来，拿到这些用户的反馈，拿到这些数据”——这正是运营的核心指标思路：上手门槛低只是拉新，反馈与数据闭环才是留存。

### ④ 智能硬件 PM（AI时代新定义）
视频通篇讲的是软件 harness，未涉及 ID 设计、MD 堆叠、电子设计 demo，因此不能据此推断 AI 在这些环节的能力边界（避免过度外推）。可迁移的信号有两点（解读/推论）：其一，视频反复出现的“内核理念—循环—上下文—工具—安全—扩展”分层，与硬件产品“定义—流程—状态—接口—合规—生态”的分层设计同构，PM 可用它审视 AI 功能在整机中的角色定位；其二，派“四工具 + bash 兜底”与 open cloud“全量工具”的对比，提示 AI 功能接入硬件时应按场景按需披露能力，而非预装全部技能，这与功耗、算力、响应延迟的取舍逻辑一致。AI 能否替代 PM 完成 ID→MD→电子 demo 全流程，本视频没有提供任何依据，不做判断。

## 精彩原句摘录
- 「带工具多的一个问题，就是它的通用性会更强，但是呢就是相当于你不做一个相关任务的时候，他也要加载这样的一些上下文的信息，所以对 token 来说就是一个冗余的消耗」（中段）——一句话讲透 agent 工具设计的核心权衡，值得记住。
- 「派最早他的极简理念中，它是不支持这个 MCP 的，但是后来经过一段时间用户的反馈和权衡，他现在也开始支持这个 MCP 了」（中段）——产品理念被用户反馈修正的鲜活样本。
- 「你要开发成一个产品，和自己用还是差别挺大的，包括这里面的 bad case，包括边缘的一些 case 有没有充分考虑」（结尾）——给所有想把手搓玩具产品化的人泼的一盆冷水。

## 适合人群
正在自建或选型 agent harness 的开发者、独立开发者，以及想理解“壳”这一层如何影响大模型使用体验的产品经理。7 分多钟就能拿到五款产品的横向对比和一套自建检查清单，性价比很高。
